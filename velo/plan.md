# Velo 协同通讯端点项目计划书

## 1. 项目概述与工程目标
Velo 是一款面向“爽k”的跨平台协同通讯应用。本项目的核心意义在于实现基本的爽k通讯需求，替换kook，oopz等商用通讯软件。并且有长期可用的屏幕共享体验。

**核心目标：**
* **能用就行：** 满足 30 人左右的日常稳定通讯即可，不过度追求极端高并发，重点关注系统的稳定性与可维护性。
* **工程范式对齐：** 核心 C++ 代码的目录组织、内存管理、多线程模型及代码风格需严格遵循 Google/Chromium C++ 标准。
* **跨平台架构：** 核心逻辑全量 C++ 化，UI 表现层交由 Android 原生实现，确保逻辑与视图的物理隔离。

---

## 2. 架构设计
整体代码结构模拟 Chromium 的组件化设计，采用分层依赖，严禁反向调用。
架构分为Android APP宿主层（代号：sk knock），C++ sdk core（代号：velo）。

### 2.1 目录结构与模块划分
在 `sdk-core` 中，按照 Chromium 的经典结构进行划分：
* **`base/` (基础库):** 提供智能指针管理（统一内存管理）、回调函数封装 (`base::Bind`, `base::Callback`)、字符串处理及基于任务的并发机制 (`TaskRunner`, `PostTask`)（统一线程池管理）。
* **`net/` (网络层):** 封装 Socket 操作，处理 TCP/UDP 数据包的收发，实现简单的自定义信令协议。
* **`media/` (媒体处理):** 负责音频重采样、简单的回声消除 (AEC) 调度、视频流/屏幕流的帧处理。
* **`jni_bridge/` (跨语言通信):** 提供规范的 C++ 与 Java 互相调用的接口封装，管理跨语言对象的生命周期。

### 2.2 Android 宿主层 (`src/`)
* **职责：** 负责设备权限申请（麦克风、录屏）、UI 组件的渲染及响应用户交互。
* **通信机制：** 通过 JNI 向 C++ 层发送指令（如“加入房间”），并通过回调接收 C++ 层的状态更新与媒体数据帧。

## 3. 核心功能描述

### 3.1 文本聊天室 (Chat)
* **需求范围：** 支持基础的文本消息广播与历史消息同步。
* **工程实践：** 使用 `net/` 模块下的长连接管理与消息队列的分发。采用序列化工具（如简单封装的 JSON 或 Protobuf）进行消息体解析。

### 3.2 多人语音室 (Voice)
* **需求范围：** 支持频道内的实时语音通话，能看清当前谁在讲话。
* **工程实践：** 对齐 Chromium WebRTC 模块的部分设计理念，处理音频设备的采集 (Android `AudioRecord`)，在 C++ `media/` 层完成 Opus 编码与混音逻辑，最后通过 `net/` 层发送至轻量级服务端。

### 3.3 屏幕共享 (Screen Share)
* **需求范围：** 允许单一用户广播设备屏幕内容，满足共享手机屏幕的需求
* **工程实践：** 调用 Android `MediaProjection` 获取视频帧，在 C++ 层实现基础的 H.264 编码循环，保证画面的清晰度和基本的流畅度。

---

## 4. 关键技术规范约定
为贴合 Chromium 维护者的开发习惯，本项目强制遵守以下规范：
1. **内存管理：** 禁用裸指针的所有权转移。强制使用 `std::unique_ptr` 管理独占资源，使用 `scoped_refptr` (或 `std::shared_ptr`) 管理共享对象。
2. **并发模型：** 抛弃裸读写锁，尽量不直接操作 `std::thread`。建立类似 Chromium 的 `MessageLoop` 机制，通过将 Task 抛入指定的线程队列来避免数据竞争。
3. **代码风格：** 严格遵循 Google C++ Style Guide（如变量命名规则、禁止使用 C++ 异常 `Exceptions`、优先使用组合而非继承）。
4. **构建系统：** 前期使用 CMake 管理依赖，结构成熟后可尝试迁移至 GN + Ninja 体系，以完全还原 Chromium 构建体验。
