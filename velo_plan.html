Velo：以 Chromium 学习为主线的可执行开发方案 v3.0

版本：3.0

项目形态：基于 Chromium 的 Android 原生通讯应用（作为学习夹具）

项目真正目标：通过一个真实可用的私有通讯应用，系统学习 Chromium 的 Android 嵌入、网络栈、Mojo/IPC、WebRTC native、Tracing 与构建系统

产品目标（次要）：小规模私有使用，支持文字聊天室、多人语音房和屏幕共享

规模目标：约 30 名用户；语音房按 2、5、10、30 逐级验证；产品指标以“能跑通”为准，不以商业 SLA 为准

部署前提：服务端运行在一台可被成员通过 Tailscale 或同类覆盖网络访问的 Linux 主机上

当前基线：Chromium 145.0.7632.218，commit d864cf709544129e9a4f101247d08628a864dcc5；Linux x64 编译环境已建立

0. 项目定位与优先级

这是一份学习型项目方案，不是商业 MVP 方案。所有决策以“最大化 Chromium 学习密度”为第一优先级，以“产出可用的私有通讯工具”为第二优先级。

优先级顺序

  1. 真实进入 Chromium 子系统：Android Content embedder、JNI、Browser Process、Network Service、Mojo、WebRTC native、Tracing。
  2. 每个阶段都有可观察、可解释、可复现的最小闭环：能画调用图、线程图、Trace。
  3. 产品功能只作为夹具：聊天、语音、屏幕共享是把 Chromium 能力串起来的线，不是终点。
  4. 服务端和运维最小化：Go + SQLite + Janus 保持够用即可，不追求高可用、多端策略、复杂权限。

明确不作为主线的内容

  • 不追求 30 人高并发稳定性，只做逐级验证。
  • 不做公开注册、找回密码、复杂权限后台。
  • 不做消息搜索、消息撤回、文件传输、录制、推送。
  • 不做 E2EE。
  • 不做产品级 UI 打磨，UI 只保证能操作、能显示状态。
  • 不先做大规模性能优化，但要做性能基线记录。

学习产出要求（贯穿全项目）

每个阶段产出以下内容，放在 src/velo/docs/learning/：

  • 调用图：本阶段涉及的类、函数、时序。
  • 线程/进程图：代码跑在哪个进程、哪个 TaskRunner。
  • Trace/日志证据：TRACE_EVENT 截图或 logcat 关键片段。
  • 源码阅读清单：本阶段涉及的 Chromium 源码路径与关键类。
  • 失败记录：卡点、复现命令、试过的方案、最终结论。
  • 最小 patch 集：本阶段对 Chromium 的改动，尽量小、尽量不动上游。

验收问题：

  1. 这条链路经过哪些进程和线程？
  2. 关键类、关键函数分别在哪？
  3. 如果我想改一个行为，最小改动点在哪？
  4. 这个子系统在真实 Chrome 里是怎么用的？我们的 embedder 缺了什么？

1. 学习主线与主攻方向

Chromium 太大，必须在项目开始就选 2–3 个主攻方向，其他作为支撑。

主攻方向

  • A. Android Content Embedder + JNI + Browser Process 生命周期
    ContentMain、BrowserMainParts、ContentBrowserClient、JNI Zero、进程模型、TaskRunner。
  • B. Chromium 网络栈
    URLLoaderFactory、NetworkContext、NetworkService、WebSocket、Cookie、代理、断网重连。
  • C. WebRTC Native 集成
    AudioDeviceModule、PeerConnection、ICE、RTP、自定义 VideoCapturer、MediaProjection。

支撑方向

  • D. Mojo/IPC 与 WebContents/Renderer：通过一个诊断 WebUI 页面接入。
  • E. Tracing / Perfetto / 日志 / 崩溃符号：贯穿全项目。
  • F. GN/Ninja/gclient/DEPS：构建系统与上游对齐。

学习产物形态

每个主攻方向结束时，应该能写出一份“如果我要在 Chromium 里改这个子系统，从哪里下手”的笔记，并附一个最小 patch。

2. 技术方案（保留 v2 骨架，微调）

2.1 客户端

  • UI：Android 原生，Kotlin + ViewModel/StateFlow。UI 是学习夹具的外壳。
  • Native 入口：通过 Chromium JNI Zero 调用 C++ VeloRuntime。
  • 运行位置：Velo C++ Core 跑在 Android 宿主进程，与 Chromium Browser Process 生命周期协同。
  • Chromium 职责：
    • 优先使用 base、任务调度、日志/Tracing、NetworkService、third_party/webrtc；
    • 新增：提供一个 WebContents 承载的内部诊断页（本地 WebUI），用于学习 Blink、Renderer、Mojo、导航。
  • WebRTC：使用 Chromium checkout 对应版本的 WebRTC native 接口，通过标准 PeerConnection 连 SFU。

2.2 服务端（降级为夹具）

  • Velo API：Go + WebSocket + SQLite。只保留最小接口：/healthz、登录、房间、消息、rtc-ticket。
  • 媒体 SFU：Janus VideoRoom 插件。只做链路验证，不做高可用。
  • 部署：Docker Compose，Tailscale 提供覆盖网络。
  • 原则：服务端任何超过 200 行的模块都要重新评估是否必要。

2.3 总体结构

Android Native UI (Kotlin)
  ├── Login / Room / Chat / Voice / Share screens
  ├── ViewModel + StateFlow
  ├── Diagnostic WebView 入口（可选）
  └── JNI Facade (JNI Zero)
          │
          ▼
VeloRuntime (C++，宿主进程 / Chromium Browser Process)
  ├── SessionService
  ├── ChatService
  ├── RoomService
  ├── RtcService
  ├── ScreenShare coordination
  ├── EventDispatcher
  └── DiagnosticsBridge (Mojo/WebUI 对接)
          │
          ├── Chromium base / task scheduling / logs / trace
          ├── Chromium NetworkService (URLLoader / WebSocket)
          ├── Chromium Mojo/IPC + WebContents (诊断页)
          └── Chromium WebRTC native API
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   Velo API (Go)        Janus VideoRoom SFU
   REST + WebSocket     WebSocket signaling + WebRTC media
          │                   │
          └──── SQLite        └──── Media streams

关键实施原则：

  • 业务状态归 Velo Core 所有；Android 只负责界面和系统权限；Chromium 提供基础能力。
  • UI 不直接操作 WebRTC 对象；ChatService 不直接访问 Android Activity。
  • 学习产物与代码同等重要：没有笔记和 Trace 的阶段不算完成。

5. 阶段 1：Android Content Embedder（学习目标：ContentMain / BrowserMainParts / 进程模型）

这是整个学习项目最关键的阶段。Linux chrome 能跑不等于 Android 嵌入链路打通。

学习目标

  • 理解 Android 上 Chromium 的进程模型：Browser Process、Renderer、GPU、Network Service、Utility。
  • 理解 ContentMain、ContentMainRunner、BrowserMainParts、ContentBrowserClient 的职责。
  • 理解 ContentShellActivity 到 native 初始化的完整路径。
  • 理解 Android Application、Activity、Service 与 Browser Process 生命周期的关系。
  • 理解 native library 加载、System.loadLibrary、libcontent_shell_content_view.so 等。

任务顺序

  1. 按 M145 Android 构建要求准备 SDK/NDK/JDK/host tools。
  2. 构建并安装 content_shell_apk，作为 Android build smoke test。
  3. 用 adb logcat 抓 content_shell 启动日志，标出 Browser Process 初始化关键点。
  4. 阅读 content/shell/android/、content/public/android/、content/app/android/ 相关源码。
  5. 创建最小 //velo/android APK target，UI 只保留一个启动页和一个按钮。
  6. 参考 ContentShellActivity 的最小接线，不复制整个 Shell UI。
  7. 由 Kotlin 调用 JNI 进入 VeloRuntime::Start()；返回结果和事件通过统一接口送回 UI。
  8. 用 LOG(INFO) 和 TRACE_EVENT 记录启动、关闭、JNI 调用及线程信息。
  9. 在 docs/learning/01_android_embedder.md 画启动时序图。

验收

  • 真机安装并启动 Velo APK。
  • 点击按钮后 Java → JNI → C++ → callback 完整。
  • C++ 启动/关闭可重复执行，无重复初始化、悬空回调或崩溃。
  • logcat 能看到 Browser Process 初始化路径和 VeloRuntime 日志。
  • 能回答：Browser Process 在哪个线程初始化？ContentMainRunner 做了什么？VeloRuntime 跑在哪个 TaskRunner？

风险处理

若 2 个短迭代内无法打通 Content 宿主，先做最小复现，确认卡点是 APK 接入、Browser Process 初始化还是 JNI 注册，再继续。

12. 阶段 8：综合夹具（文字聊天 + 多人语音 + 屏幕共享）

到这里才把学习成果串成完整产品。服务端和 Janus 保持最小化。

文字聊天

  • 登录、房间列表、消息页。
  • client_msg_id + (sender_id, client_msg_id) 唯一约束防重复。
  • ACK、发送中/失败状态、历史分页、自动重连、重连补拉。
  • 验收：两设备实时收发、历史恢复、断网重发只出现一次。

多人语音

  • VoiceSession 生命周期接入 RoomService。
  • 服务端管理 Velo room 与 Janus VideoRoom 映射；客户端只拿临时凭据。
  • 断线先恢复 WebSocket，再决定复用或重建 PeerConnection。
  • 记录入房耗时、ICE 完成耗时、首音频时间、掉线次数、重连耗时、CPU/内存。
  • 逐级压测：2 人 30 分钟、5 人、10 人 60 分钟、30 人先验证成员列表与状态。
  • 允许设定明确媒体参与上限，超过时 UI 提示。

屏幕共享

  • 沿用阶段 6 实现，接入房间 UI。
  • 任一时刻最多一个共享者。
  • 语音 + 共享同时运行 30 分钟并记录指标。

稳定性

  • 测试安装、升级、服务端重启、客户端重启、数据库迁移。
  • 测试 24 小时空闲连接、频繁进出房间、反复开始/停止共享、网络切换、前后台切换。
  • 数据库自动备份与恢复演练。
  • 配置文件与密钥不进 Git。

  1. 确认分支状态，保存 M145 baseline tag，创建 velo/mvp 分支。
  2. 保存 args.gn 到 src/velo/config/m145_devrelease.args.gn。
  3. 按 M145 Android 文档准备构建依赖；不改动当前 Linux out/m145_release。
  4. 构建并安装 content_shell_apk，抓 logcat，标出 Browser Process 初始化关键点。
  5. 阅读 content/shell/android/、content/public/android/、content/app/android/，写第一份学习笔记。
  6. 建最小 //velo/android target，打通 Kotlin → JNI → C++ VeloRuntime::Start/Stop/Ping。
  7. 起一个最小 /healthz Go 服务，让 C++ Core 通过 Chromium 网络能力请求它。

15. 开发规则（学习型项目版）

  1. 一条链路先闭环。每次只推进一个可验收的端到端能力。
  2. 先使用 Chromium 现有机制。Network、任务调度、JNI、日志、WebRTC 优先用对应版本内已有正式接口。
  3. 禁止未验证的大抽象。一个模块至少有实际调用者和测试后再抽象。
  4. 状态只有一个所有者。Room/Chat/RTC 状态由 C++ Core 或服务端明确拥有；UI 只展示并发命令。
  5. 每个跨层调用都定义失败语义。JNI 错误、HTTP 错误、WebSocket 断开、ICE 失败、权限拒绝都要有状态和恢复策略。
  6. 每阶段记录命令与结果。构建命令、测试设备、服务端版本、复现步骤、失败日志。不写无法验收的“已完成”。
  7. 不做没有基线的优化。先记录真实启动时间、连接时间、首消息、入房、首音频、首帧，再决定优化。
  8. 尽量不动上游。对 Chromium 的改动要小、要记录、要能 rebase。定期检查上游是否已有更合适的接口。
  9. 主动对比真实 Chrome。每学一个子系统，问：真实 Chrome 怎么用？我们的 embedder 缺了什么？这本身是最有价值的学习产物。
